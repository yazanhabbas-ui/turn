# Architecture decisions and defaults

Each entry records a choice, its reasons, and how to revisit it. Newest entries are at the end.

## D1: One Node process: Next.js with a custom server (not NestJS)

- **Choice:** Next.js App Router for pages and REST route handlers. A small `server.ts` hosts Next, the Socket.IO hub and the background jobs in the same process.
- **Why:** one deployable and one language for the single on-prem box, with types shared between UI and API. Route handlers cannot hold WebSockets, hence the custom server.
- **Escape hatch:** business logic lives in `src/domain` (pure) and `src/server` (services), with no Next.js imports except request plumbing. It can move behind NestJS or a separate API process without a rewrite.

## D2: Drizzle ORM + PostgreSQL 16

- **Why:** SQL-first. Queue correctness needs `SELECT … FOR UPDATE`, advisory locks and conditional updates. Reports need `percentile_cont`, `generate_series` and window functions. Migrations are plain SQL files in `drizzle/`, reviewed and committed.
- PostgreSQL 15+ is required because `UNIQUE NULLS NOT DISTINCT` is used for scoped settings and role grants.

## D3: Own session layer on @oslojs + argon2id (not Auth.js / Lucia)

- **Why:** Lucia was deprecated (2025) and now recommends this approach. The Auth.js credentials provider does not support database sessions well.
- **How it works:**
  - The cookie holds a random 160-bit token. The database stores only its SHA-256, so a DB leak cannot hijack sessions.
  - Sessions have sliding expiry (`SESSION_TTL_HOURS`).
  - "Force logout" deletes the user's session rows.
  - Passwords use argon2id (19 MiB, t=2).
  - TOTP secrets are AES-256-GCM encrypted with `APP_ENCRYPTION_KEY`.
- **OIDC-ready:** the `oidc_accounts` table links external identities (Entra ID, Google) to users. A future OIDC callback creates the same DB session, so nothing else changes.
- **Login hardening:**
  - Accounts lock after N failures (settings: `security.maxFailedLogins`, `lockoutMinutes`).
  - Login is rate-limited per IP.
  - Unknown emails still run a password verification, so timing does not reveal whether an account exists.

## D4: CSRF and cookies

- Cookies are `HttpOnly` and `SameSite=Lax`, and `Secure` when `APP_URL` is https (overridable by `COOKIE_SECURE`).
- Every mutating API call must carry an `Origin` (or `Referer`) matching the host or `APP_URL`, or it is rejected with `bad_origin`.
- API-key clients (integrations) will authenticate with an `Authorization` header and are exempt.

## D5: RBAC model

- Permissions are a code catalogue (`src/domain/rbac/permissions.ts`), synced to the `permissions` table by the seed.
- Roles are data. **Built-in roles are `admin`, `receptionist` and `agent`**: they are flagged `is_system`, cannot be deleted, and their permissions are re-synced from code on each seed. The display is a _device_ (token-authenticated), not a role.
- A role grant (`user_roles`) is optionally scoped to a branch (`branch_id` null means all branches).
- `can(grants, permission, branchId)` is the single check. Every data query is additionally filtered by `organization_id` and by the branches the user may access.
- **Supervisor** is seeded as an example _custom_ role (reports + reassign, no settings), showing how admins build roles from the matrix.

## D6: Internationalization

- `next-intl` with `messages/<locale>.json`. Arabic is the default locale (served at `/…`); English is at `/en/…`.
- A unit test asserts every locale has exactly the same keys and no empty strings.
- **User-entered content** (reason names, templates, branch names) is stored as JSONB `{ "ar": "…", "en": "…" }`. Adding Kurdish, Farsi, Urdu or French needs a messages file and a line in `src/i18n/locales.ts`, with no schema change.
- Message keys may not contain dots, so permission labels are nested (`permissions.tickets.issue`).
- **RTL:** `<html dir>` follows the locale. shadcn/ui components were generated with `rtl: true`, so they use logical properties (`ms-*`, `pe-*`, `start-*`). Directional icons get the `.rtl-flip` class.
- **Digits:** Western or Eastern Arabic-Indic, set separately for screens, tickets and voice (setting `regional.digits*`). Typed Eastern digits (e.g. in 2FA codes) are accepted everywhere.

## D7: Arabic name search

- `normalizeArabic` folds alef forms (أ إ آ ٱ → ا), ى → ي, ة → ه, ؤ/ئ, Persian letters, diacritics and tatweel.
- `nameSkeleton` reduces Arabic and Latin spellings to the same consonant skeleton (محمد = Mohammed = Muhammad = mhmd) for loose cross-script matching.
- Normalized values are stored in `*_search` / `*_translit` columns so they can be indexed.

## D8: Settings are typed key/value rows

- Every setting key has a Zod schema with defaults in `src/server/settings/registry.ts`.
- Stored values are merged in this order: defaults ← organization row ← branch row. Fields added in later versions fill in automatically.
- Nothing business-related is hard-coded: branding, digits, time format, Hijri, ticket numbering, password policy, lockout, invite expiry, data retention, consent text and visitor status page are all settings.

## D9: White-label

- Branding (company name, logo, colours, font, welcome text, ticket footer) is a setting and is applied as CSS variables (`--brand-primary`, `--brand-font`) on `<html>`.
- Fonts (IBM Plex Sans Arabic, Cairo, Tajawal) are bundled via `@fontsource`, so there are no Google Fonts calls at runtime.

## D10: Privacy by design (Saudi PDPL / UAE PDPL)

- Visitor fields are minimal and optional per reason (`intake_fields`).
- Phone numbers are also stored as a keyed hash (`PHONE_HASH_KEY`) for sticky routing. A retention job (hardening milestone) anonymizes visitors after `privacy.retentionDays` (default 90) and keeps the hash-free statistics.
- Logs redact phones, emails and tokens. `notifications_log` stores masked recipients only.
- There is no third-party tracking, CDN or analytics.

## D11: Realtime

- Socket.IO is attached to the same HTTP server, with connection-state recovery (2 minutes) and automatic long-polling fallback.
- Rooms per org, branch, user and display. The server is the single source of truth: clients only render events.
- With `REDIS_URL` set, the Redis adapter (realtime milestone) allows multiple app nodes. Without it, a single node runs in-memory.

## D12: Multi-tenancy

- Every table carries `organization_id`, and branch-scoped tables also carry `branch_id`. The UI assumes one organization per deployment (on-prem). Public pages (login, display) use the first organization.

## D13: Time and ticket numbers

- All timestamps are `timestamptz` in UTC. Each branch has an IANA timezone for display and business-day calculation.
- Tickets belong to a **service day**: branch-local, with a rollover at the `ticketing.dailyResetTime` setting (default 03:00, so late shifts do not reset mid-evening).
- Numbers are unique per `(branch, service_day, prefix, number)`, enforced by a unique index. They are allocated from `ticket_counters` under a row lock.

## D14: Test database safety

- Integration tests truncate tables, so `tests/setup-env.ts` forces a database whose name ends in `_test` and refuses to run otherwise.

## D15: Offline ticket issuing is deferred

- The local server keeps everything working when the _internet_ drops.
- Issuing tickets while the _local server itself_ is unreachable (the section 10 stretch goal) is deferred to the hardening milestone as optional. The planned design: pre-reserved per-device number blocks, with sync on reconnect.

## D16: UTF-8 databases are mandatory

- Postgres clusters initialised on Windows default to WIN1252, and every Arabic insert then fails. `runMigrations()` refuses to run unless the database encoding is UTF8. Test databases are created with `ENCODING 'UTF8' TEMPLATE template0`.

## D17: Admin guard rails

- **No privilege escalation:** a user cannot create a role, assign a role, or send an invite that carries a permission they do not hold themselves.
- **Branch-scoped managers:** a user whose `users.manage` is limited to certain branches only edits grants in those branches. Grants in other branches are preserved untouched.
- **Last administrator:** after any user change, at least one active user must keep an organization-wide grant with `roles.manage`. You cannot deactivate yourself.
- **Built-in roles are read-only in the UI and API.** They are re-synced from code on every seed, so edits would be lost. Clone a built-in role to customise it. A custom role can only be archived once no user holds it.
- **Nothing that history references is hard-deleted:** reasons, branches, desks, floors, roles and groups are archived. Nothing else is deleted outright because no history references them.

## D18: Invites and password resets

- Tokens are random, single-use, and stored only as SHA-256. They are claimed with an atomic `UPDATE … WHERE used_at IS NULL`.
- The invite link is always shown to the admin, so a "copy link" fallback works with no email or WhatsApp provider configured. **Resend rotates the token**, so the old link stops working.
- Accepting an invite for a role with `agent.serve` creates an agent profile in the invited branch (or the default branch).
- "Add user" without a password returns a 72-hour set-password link. An admin reset gives a 24-hour link and signs the user out everywhere.
- The invite expiry comes from the `security.inviteExpiryHours` setting.

## D19: Messaging and jobs

- **Providers:** `MessageProvider` (in `src/server/messaging`) has an SMTP email implementation and a mock (`MESSAGING_MOCK=true`, which records to an in-memory outbox). WhatsApp and SMS adapters arrive in the messaging milestone. Until then those channels report `not_configured` and the admin copies the link.
- **Templates:** messages always render from the organization's `message_templates` for (channel, event), in the recipient's language.
- **Delivery log:** every send is logged in `notifications_log` with a masked recipient.
- **Jobs:** delivery runs through pg-boss (`messages.send`, 5 retries with backoff). When the worker is not running (tests, CLI scripts), `enqueue` runs the handler inline, so behaviour is identical.

## D20: Admin UI conventions

- Forms use native `<select>` and checkboxes (styled) rather than custom popups. They work on every tablet and kiosk browser, with screen readers, and in RTL without positioning bugs.
- Bilingual fields are edited side by side (Arabic first), each with its own `dir`.
- Counts use ICU plural rules (Arabic has zero/one/two/few/many/other forms). Lists are joined with `Intl.ListFormat`, so the separator follows the locale.
- Visit-reason and priority icons come from a curated, statically bundled lucide set (`src/components/app/entity-icon.tsx`). The database stores the icon key.

## D21: Docker-free local runtime (`npm run local`)

- **Why:** the development PC has no CPU virtualization, WSL2 or admin rights, so Docker Desktop, Podman and Rancher Desktop cannot run there. Decided with the product owner on 2026-09-29.
- **What:** `scripts/local.ts` starts a bundled PostgreSQL from the `embedded-postgres` dev dependency. The cluster is UTF-8, uses locale C, stores data in `./.local/pgdata`, and listens on port 5433. The script creates the `dor` and `dor_test` databases, writes `.env` with random keys on first run, applies migrations, runs the idempotent seed, and starts the app in dev or production mode.
- **Scope:** Docker Compose remains the supported production deployment. The Definition of Done's `docker compose up` must still be verified on a machine with Docker.

## D22: Queue engine architecture

- `src/domain/distribution` is pure and I/O-free: config schema and layering, ordering and scoring, strategies, eligibility, dispatch and reservation expiry. The server builds an in-memory snapshot of the branch under its lock and asks the engine. The Simulate screen runs **the same functions** in a discrete-event simulation, so its results reflect real behaviour.
- **Rule layering:** queue → branch → global → defaults, deep-merged. Arrays (such as strategy chains and aging steps) replace rather than merge. An invalid stored layer is ignored, so a mistake cannot break the queue. Rules are read on every decision, so changes need no restart.
- **Strategy chain:** each strategy keeps only the best-ranked agents, and the next one breaks ties. Adding a strategy means adding one function to `STRATEGIES`.
- **Ordering score:** wait × waitWeight + priority × priorityWeight + aging boosts + SLA pressure + appointment boost. Tiers order the queue: max-wait-breached first (FIFO among them), then priority lanes, then the regular line. Ties are broken by queue time, then id.
- **Queue time:** `queued_at` is the ordering clock. A transfer keeps it, so the visitor keeps their place. "Send to end of queue" resets it. Waiting-time reports use `arrived_at`.
- **Agent statuses:** only AVAILABLE agents receive new work. BUSY keeps existing reservations but gets nothing new. Break, away and offline release reservations. Pressing Call next sets the agent to AVAILABLE.
- **Backups** serve a reason only during overflow (queue length or wait over the limit), or when no primary agent is free (configurable).
- **Hybrid and sticky reservations** expire after `hybrid.acceptTimeoutMinutes`. An expired hybrid reservation raises a supervisor alert. Pure push reservations do not expire while the agent is present.
- **Manual mode** never hands out unassigned tickets: reception or a supervisor assigns them.

## D23: Consistency guarantees

- Every branch mutation takes a transaction-scoped advisory lock on the branch, then updates tickets with `WHERE status = expected AND version = expected`.
- Numbers come from `ticket_counters` under the same lock and are protected by a unique index on (branch, service day, prefix, number).
- Issuing is idempotent through an `Idempotency-Key` (unique per organization).
- Integration tests fire concurrent Call next and concurrent issuing, and assert no duplicates.
- A 15-second maintenance loop evaluates automatic recalls, no-show timeouts, hybrid releases and push dispatch per branch. It is safe on several nodes, because every pass takes the branch lock.
- Time comes from `src/server/clock.ts`, which tests can move forward to exercise timeouts deterministically.

## D24: Issuing rules

- **Data minimisation:** only the reason's configured intake fields are accepted; anything else is rejected. Required fields are enforced. When personal data is provided and `privacy.requireConsent` is on, consent is required.
- Phones are normalized (Western digits, `00` becomes `+`) and hashed with `PHONE_HASH_KEY` to recognise returning visitors.

## D25: Charts

- ECharts (tree-shaken, SVG renderer) with the validated reference categorical palette: slots 1–4 pass the CVD and normal-vision checks in light and dark mode.
- Chart axes run left to right in both languages; labels are localized.
- Text is measured with the page's computed font, because Arabic glyph widths differ from the default font.
- Every chart has a table alternative on the same page.

## D26: Local performance (measured on the Windows development PC)

- **Dual-stack listening:** the server listens on `::`, which accepts IPv4 and IPv6, and falls back to IPv4 automatically. Listening on `0.0.0.0` only made every new connection to `localhost` on Windows wait ~210 ms for the IPv6 attempt to fail. `HOSTNAME` still overrides the address.
- **`npm run local` defaults to production:** it rebuilds into `.next-prod` only when sources changed, skipping lint and typecheck (`DOR_FAST_BUILD=1`) because CI runs them. Warm pages take ~50–100 ms and API calls ~10–40 ms. Before, in dev mode over `localhost`, pages took 0.5–11 s and API calls ~250 ms.
- **`--dev` uses webpack:** measured warm requests are ~45 ms with webpack versus ~450 ms with Turbopack under this custom server. `DEV_BUNDLER=turbopack` opts in. The file watcher excludes `src/` and `messages/`, because Next hot-reloads those itself; restarting the process would discard its compile cache. A warm-up pass pre-compiles the main pages after startup.
- **Background jobs:** a failure to start pg-boss (for example a transient database reset) is retried and never takes the app down. If the worker is unavailable, job handlers run inline.

## D27: Reception and agent screens

- **Realtime:** one shared Socket.IO connection per tab. It subscribes to the branch room and refetches on `queue.updated`, `ticket.called` and `agent.updated`, with bursts debounced to one refetch. While disconnected, pages poll every 5 s and show a "Reconnecting / Offline" pill; after reconnecting they refetch. Measured: reception issues a ticket and the agent's screen updates within 10–110 ms.
- **Two taps to issue:** tap a reason (featured reasons come first, and each has a keyboard shortcut), then tap **Issue**. Only the reason's configured intake fields are shown; optional ones stay collapsed. The consent checkbox appears only once personal data has been typed. Every issue attempt carries an idempotency key, which is kept on retry, so a network error never creates a second ticket.
- **Agent:** one big button changes with the state (Call next → Start service → Complete), and Enter triggers it (a USB keypad or call button works too); R recalls. No-show and complete show an 8-second Undo. Hold returns the visitor to the same agent. Transfer can go to another reason and/or a specific agent, with a note.
- **Personal data minimisation:** visitor details in the live queue are visible to people who issue, edit or reassign tickets. Agents see details only for tickets reserved for or served by them (`queueState`).
- **Printing:** the ticket prints from the editable bilingual `ticket_print` template, in the visitor's language and the configured ticket digits. An 80 mm `@page` print stylesheet works with ESC/POS thermal printers through the OS driver. The QR code (optional setting) links to `/t/<token>`, generated in the browser with no external service. Auto-print is a per-device setting kept in local storage.
- **PWA:** the web manifest takes its name and colour from the branding settings. The service worker caches only hashed static assets, fonts and icons (cache-first) and pages (network-first, falling back to the last copy). It never caches the API or realtime traffic. It registers in production only.
- **Visitor status page** `/t/<token>` (basic version; notifications arrive in Milestone 7): opens in the language chosen at reception and refreshes every 10 s until the ticket is finished.

## D28: Visit reasons are always open by default

- Decided with the product owner on 2026-09-29: no working-hours restriction by default. The demo seed no longer attaches a timetable to visit reasons, so tickets can be issued at any time.
- The working-hours feature itself is kept: timetables (with Ramadan hours) and cut-off still apply to any reason that is given a timetable in Admin → Visit reasons. The demo seed still creates an example timetable ("Office hours", Sunday–Thursday 08:00–16:00), unattached, ready to use.

## D29: No pauses, no holidays

- Decided with the product owner on 2026-09-29: service pauses (prayer and custom), holidays and closures are removed entirely. Reception controls the flow: if nobody prints a ticket, nobody is waiting, so the system never needs to block issuing or calling by time of day.
- Removed: the `pause_windows` and `holidays` tables, the branch latitude/longitude (they existed only for offline prayer times), the `adhan` dependency, the API routes, the admin UI sections, the pause banners and the `paused` reason of call-next. Migration `0001_remove_pauses_holidays`.
- Break types (including a prayer break an agent takes) are unrelated and stay.

## D30: No working hours

- Decided with the product owner on 2026-09-29, superseding D28: working hours are removed entirely. Visit reasons are always open and tickets can be issued at any time; reception decides when to issue.
- Removed: timetables and Ramadan hours (`schedules`, `schedule_rules`, the reason `schedule_id` and `cutoff_minutes` columns, the Ramadan mode setting), the Working hours admin page and API, the open/closed state on the reception screen, and the `closed` / `cutoff` ticket errors. Migration `0002_remove_working_hours`.
- The service day and ticket numbering reset time (`dailyResetTime`) stay: they are about numbering, not opening hours.

## D31: Display screens and voice

- **Pairing:** an admin creates a screen under Admin → Screens and gets a 6-character single-use code (valid 15 minutes). The TV opens `/display` and the code is typed there (or `/display?code=…`). The server returns a 160-bit device token once and stores only its SHA-256. The token lives in the TV browser storage and is sent as a Bearer header and as the Socket.IO handshake auth. Revoking, deleting or re-pairing kills the old token immediately and disconnects the socket; the TV returns to the pairing page.
- **Least data:** a screen receives ticket numbers, desk numbers, reason names and counts only. Its socket joins a separate `screens:<branch>` room that carries `queue.updated` and `ticket.called` (without the agent id), never alerts or agent status. Screens are read-only.
- **Layouts:** classic (row per desk), single (one giant number) and multi-zone (latest call, desks, slides, waiting counts), always with dark theme, ticker, clock, optional Hijri date and configured digits. Desks can be filtered by zone per screen. The language rotates between Arabic and English (or stays on one).
- **Resilience:** the last state is cached in local storage, the screen keeps showing it during a network drop, polls every 5 s while the socket is down, retries with back-off, and shows a reconnecting badge. It requests a wake lock and offers fullscreen (F, double click or the corner button).
- **Voice:** a call plays a generated chime, then each language of the sequence (or only the visitor language), repeated N times, in a queue that never overlaps. Phrases are the editable `voice/ticket_called` template (`ticket_recalled` is used for recalls when it exists). The ticket is spoken as letters plus the number without leading zeros (`A-014` → "A 14") in the voice digit system. Providers implement one interface: the browser engine (default), pre-recorded clip packs (`ar.digit.7`, `ar.letter.A`, `ar.phrase.number`…) for PCs without an Arabic voice, and cloud TTS as an extension point (it behaves like the browser provider until an adapter is added). A language with no usable voice is skipped and shown as sound trouble rather than blocking the queue.
- **Audio unlock:** browsers block sound until a gesture. If the audio context starts suspended, a full-screen "touch to enable sound" splash appears, and any tap or key press unlocks it. Kiosk Chrome started with `--autoplay-policy=no-user-gesture-required` skips the splash.
- **Defaults chosen:** voice settings are organization-wide (`voice` setting) with per-screen overrides for enabled, volume and rate. Media in ticker slides and audio packs must be local paths or inline data, never third-party URLs.

## D32: Faster ticket issuing at reception

- Requested by the product owner: fewer steps to print a ticket, with the collected data configurable, on the basis that only the receptionist types visitor data.
- **One tap:** a visit reason with no required intake fields issues its ticket on the first tap or shortcut key, and prints at once. Reasons with required fields, manual-distribution reasons and appointment check-ins still open the form, focused on the first required field, and Enter submits.
- **Priority and language moved above the reasons** (chips and a toggle) and are chosen before the tap. Priority resets to normal after each ticket; the language sticks per device. Both can be hidden.
- **No blocking dialog:** after issuing, a small banner (number, people ahead, wait, reprint) replaces the confirmation window, so the next visitor can be served immediately. The old window remains as an option.
- **Configurable:** Admin → Settings → Reception (the reception setting: one-tap, after-issue behaviour, auto-print default, priority and language choices, default language). Which data is collected, and whether it is required, stays per visit reason (Visit reasons → Visitor information to collect). The consent question is switched off with Data protection → require consent.
- **Auto-print** defaults to on; each reception PC can override it (kept in local storage). Silent printing needs Chrome started with `--kiosk-printing`.

## D33: Reports, wallboard and alerts

- **One computation path:** every KPI is computed by pure functions in `src/domain/reports/compute.ts` from flat "ticket facts" (arrival, first call, start, finish, status, recalls, transfers, returning) and the agent status log. The service only fetches and filters. This is what the unit tests pin down, and what CSV, Excel, PDF, the page and the scheduled emails all share.
- **Definitions** (so numbers are comparable): _wait_ = arrival to the FIRST call (recalls do not extend it); _service time_ = start to finish of completed tickets; _SLA compliance_ = called tickets whose wait was within their reason's target; _service level_ = called tickets within N minutes (settings, default 80% within 5); _abandonment_ = (no-show + cancelled) / visitors, and the wait before abandonment ends at the cancel or at the unanswered call; _utilisation_ = time serving / (logged-in time minus break time); _idle_ = available time minus serving time; _fairness_ = Jain's index over served counts of agents who worked (1 = perfectly even); _returning_ = the visitor had an earlier ticket (matched by the phone hash, no numbers stored).
- **Time zones:** date ranges are service days of the selected branch; hour/weekday buckets use each branch's own time zone. A range is limited to 92 days so a report stays interactive.
- **Forecast:** deliberately simple and explainable: the mean of the same weekday over the last N days (default 28), by day for the next week and by hour for tomorrow. Suggested agents = expected arrivals × average service minutes ÷ (60 × target utilisation, default 80%).
- **Anomaly alerts** (`alerts` setting, evaluated every minute per active branch): a visitor waiting too long, too many waiting, an available agent idle while people wait, and a no-show spike. Each is stored once (an hour of silence, or until acknowledged), shown live on the wallboard, pushed over Socket.IO, and optionally emailed to supervisors.
- **Wallboard** shows ticket numbers and counts only, never visitor details. Reports and the wallboard are branch-scoped by the viewer's grants.
- **Exports:** CSV with a UTF-8 BOM and formula-injection protection, Excel with right-to-left sheets for Arabic, PDF with shaped Arabic text. Scheduled reports cover the previous day or week and are emailed with the file attached.
- **CSAT** (visitor feedback) arrived with Milestone 7 part B and is in the reports: see D53.
- **Demo history:** `npm run db:history` (opt-in) creates a synthetic past so reports have data; `-- --purge` removes exactly what it created.

## D34: Bundled Arabic voice

- Most kiosk PCs (including this one) have no Arabic text-to-speech voice, and installing one needs administrator rights and the internet. The project therefore ships a pre-recorded Arabic pack: 66 clips (phrase "رقم", the desk phrase, digits 0-9, Latin A-Z and Arabic letter names) in `public/audio/ar`, generated offline with Piper and its `ar_JO-kareem-medium` voice. `npm run voice:install-arabic` registers the pack and switches the provider to pre-recorded clips; Arabic then plays from the clips while English still uses the browser voice.
- The pack speaks a ticket as "رقم" + letter + each digit + the desk phrase + the desk digits (for example A-012 at desk 1: "number, A, one, two, please go to desk, one"). Other phrase wording only applies to the browser voice.
- **Licence:** the voice model's dataset licence is listed as "see URL" (github.com/AliMokhammad/arabicttstrain). Confirm it allows commercial redistribution before shipping this pack to customers, or record your own clips into the same file names.

## D35: Choosing the Arabic voice in the admin panel

- Seven Arabic voices ship as pre-recorded packs in `public/audio/ar/<id>/` (66 clips each, listed in `catalog.json`): Microsoft neural voices Hamed (Saudi), Hamdan (Emirati), Fahed (Kuwaiti), Rami (Lebanese), Ismael (Algerian), Jamal (Moroccan), and the offline Piper voice Kareem (Jordanian). Admin → Screens → Voice → "Arabic announcement voice" lists them with a preview button (it plays a sample ticket from the pack's own clips) and a "Use this voice" button. Choosing one activates its pack (one active pack per language), switches the provider to pre-recorded clips, and reaches every paired screen at once. "Browser voice" switches back to the screen device's own voice. "Add the bundled voices" (or `npm run voice:install-arabic`) registers them for an organization.
- **Licence caveat:** the six Microsoft clips were generated with the unofficial Edge read-aloud service, which is fine for evaluation but is not a licensed production route. Before shipping to customers, regenerate them with an Azure Speech key (same voice names) or record your own clips using the same file names. The Piper voice's dataset licence is also unconfirmed (see D34).
- Custom packs can still be added by hand under "Audio packs" in the same tab.

## D36: Several visitors per agent, wallboard branding, logo and font

- **Several visitors at once** is an organization setting (Admin → Settings → Agents), off by default. When off, every agent serves one visitor at a time. When on, an agent's limit is their own number (Users → agent profile; empty = the organization default, default 2). The distribution engine already counted an agent's called and serving tickets against a limit, so the rule is applied where agents are loaded (`snapshot.ts`); nothing else changes. The agent screen shows the visitors as tabs ("2 of 3 visitors"), a new call takes focus, a "Call another visitor" button appears while there is room, and Enter/actions work on the visitor in focus. Display screens list every ticket of a desk, and the wallboard shows all of an agent's visitors on the desk card. `agent_profiles.max_concurrent` became nullable for this (migration 0004; existing 1s became "organization default").
- **Wallboard branding** (`wallboard` setting, Admin → Settings → Wallboard): theme dark, light or dark tinted with the brand colour, an optional own title, show/hide logo, company name, branch and clock, and a text size of 80-160% for far-away screens. The logo, primary/accent colours and font always come from Branding, so one change re-brands the whole product. The logo sits on a light plate on dark screens because most logos are drawn for a light background.
- **Logo:** the supplied 15499 x 5947 px PNG (700 KB, ~370 MB decoded) was resized to 1200 px (`public/branding/yallago-logo.png`, 43 KB) and 400 px; huge images can crash a TV browser. The original stays in `assets/`.
- **Font:** "FF Hekaya Light" is bundled (`public/fonts`, declared in globals.css) and selectable under Branding → Font. It covers Arabic letters and digits, Latin and punctuation, but it is a single Light weight (bold text is synthesized by the browser). Confirm your licence covers web embedding on customer sites; the readme in the font folder contains no licence text.

## D37: Round robin distribution mode

- New mode **Round robin** (Admin → Distribution): every new ticket goes to the next agent in a fixed rotation. The engine treats it as auto-assign with the `rotation` strategy (`toEngineConfig`), so reservation, capacity, hybrid timeouts and the simulator all keep working. The rotation is stateless: it continues after the agent who received the queue's previous ticket (read from `tickets.assigned_agent_id`), in agent-id order, skipping agents who are away, full or not skilled for the reason, and wraps around. `rotation` is also available as a step in the auto-assign strategy chain.
- The older strategy named "Round robin" (least recently assigned) is now labelled **Least recently assigned** to avoid confusion; its key `round_robin` in stored rules is unchanged. Note: the mode key `round_robin` and that strategy key share a name in stored data, but they are different settings (`mode` vs `push.strategies`).

## D41: Agent shifts

- Shifts (`shifts`, organization-wide; defaults Morning 08:00-15:00 and Evening 15:00-22:00) say when an agent works; a shift whose end is not after its start runs past midnight. An agent has at most one (Users → agent profile). This is about staff, not about the service: the queue itself is never closed by time of day (D29, D30).

## D42: Limit on simultaneous breaks

- Setting `breaks` (Admin → Settings → Breaks; on by default with 2 agents at a time and a 3-minute hold): the most agents of a branch that may be on a break at once, as a fixed number or a percentage of signed-in agents (at least one), and how long an offered place is held (`holdMinutes`).
- When the limit is reached an agent's status does not change; they join a first-in-first-out line (`break_requests`), are told how many colleagues are on a break and their place, and receive a `break.update` event (only to that agent) when a place is free. The place is held for them for `holdMinutes`; if unused it passes to the next agent and the first goes to the back if they ask again. The line is served by every status change and by the periodic maintenance.

## D47: Waiting-time estimate

The waiting time on the ticket, the issue confirmation, the visitor page, the wallboard and the queue views is one figure from one place: `BranchContext.wait` (`src/server/queue/wait-analytics.ts`), driven by the setting group `waitEstimate` (organization default, overridable per branch like Wi-Fi). It is only an estimate and never blocks issuing or calling (D29, D30).

- **How long one visitor takes (`mode`):** `reason` (default, the previous behaviour: each reason's expected minutes), `fixed` (`fixedMinutesPerVisitor`, 0.5-120) or `analytics` (learned from completed tickets, `finishedAt - startedAt`). `divideByAgents` decides whether the queue is divided by the agents serving it.
- **Analytics:** looks back `lookbackDays` (default 14); below `minSamples` (default 20) valid services of a reason its expected time is used and the admin sees "Learning: 8 of 20". `statistic` is median (default, robust), average or p75 (cautious). `trimOutliers` drops services under 20 seconds or over 4 hours and the fastest and slowest 5%. `weightByHour` uses only services within one hour of now (the same weekday first) when there are enough of them, otherwise all. Weekends are not hard-coded, so there is no weekday-type rule beyond the same weekday.
- **Cost:** one light query per branch, cached for 5 minutes, and only in analytics mode; it runs in a savepoint and any failure falls back to the reason's own time, so issuing is never slowed or failed by it.
- **Shape:** `rounding` (up to 1, 5 or 10 minutes), `bufferPercent` safety margin, `showAsRange` ("10-15 min" from the p25-p75 of real services, or +/-25% in the other modes), `minShown` (below it the visitor sees the "next" text instead of a number).
- **Wording** (all bilingual and editable): `label` (default "Estimated wait"), `unitLabel`, `nextText`, `disclaimer` (optional small note). `showOnTicket` off hides the figure on the printed ticket, the confirmation and the status page. The printed ticket uses the ticket's language. Template lines containing `{wait}` are no longer printed: the wait line comes from these settings so an old template cannot show a second, different number (the seed template no longer carries `{wait}`).
- **Admin:** Settings, "Waiting time" tab: mode cards, only the fields of the chosen mode, a live preview (1, 3, 6 and 10 ahead) and, in analytics mode, a table of real samples, median, average and p75 against the expected time and the value in use. The table is `GET /api/v1/admin/wait-analytics?branchId=` (reports.view on that branch, organization-wide without `branchId`).

## D53: Visitor feedback (CSAT)

- **What is asked.** After a visit is COMPLETED the visitor rates it 1 to 5 (faces or stars, setting `feedback.style`), and optionally leaves a comment (up to 500 characters) and answers a 0 to 10 "would you recommend us" question (NPS, off by default). No-shows and cancelled tickets cannot be rated. One answer per ticket (`csat_responses.ticket_id` is unique); a second attempt gets `409 conflict` and the card simply shows the thank-you.
- **Where.** The card sits on the status page `/t/<token>` once the ticket is completed (`feedback.showOnStatusPage`), and `/t/<token>/feedback` opens the same page with the card scrolled into view and focused (also when the status page hides it). `feedbackLinkFor(ticket)` (`src/server/feedback/links.ts`) returns the absolute link from `APP_URL`, in the visitor's language; notifications put it in messages as `{feedbackLink}`. The link is not separately signed: the ticket's random public token is already the credential of the QR page and reveals no personal data. Channel is recorded as `status_page` (card), `link` (opened from the feedback link) or `kiosk` (reserved for an in-branch device; nothing sends it yet).
- **API.** `POST /api/v1/public/tickets/:token/feedback`, no login, 20/min per IP; the token must belong to a completed ticket and the ticket must be unanswered (`404` unknown token or feedback off, `409 invalid_transition` not completed, `409 conflict` already answered, `400` validation). The comment and NPS are kept only if the settings ask for them. The status API returns `feedback` (the card's texts and options, `answered`) only for completed tickets.
- **Settings** (group `feedback`, branch-overridable, Settings, Visitors & tickets, Feedback): `enabled`, `showOnStatusPage`, `style` (stars or faces), `askComment`, `askNps`, `lowScoreThreshold` (default 2), and the editable bilingual texts `prompt`, `commentPrompt`, `npsPrompt`, `thanks`. Also `wallboard.showCsat` (default on) and, in `alerts`, `lowScoreAlerts` (default on), `lowSatisfactionBelow` (0 = off), `lowSatisfactionMinResponses` and `lowSatisfactionWindowHours`.
- **Reports.** `ReportData.csat`: average score, satisfied share (4 or 5), response rate (answers over completed visits), NPS when asked, distribution 1 to 5, by agent, reason, branch, shift and day, and the latest low-score comments (visitor name shown, number masked unless `visitors.privacy`, like the repeat-visits table). Answers are matched to the tickets of the period and follow every report filter. The agents table has a satisfaction column. Export sections: `csatSummary`, `csatDistribution`, `csatByDay`, `csatBreakdown`, `csatComments` (all in CSV, Excel and PDF; in the default full report only when somebody answered; a "Visitor satisfaction" quick pick in the download dialog).
- **Alerts.** `low_score` (an answer at or below the threshold in the last hour; raised at once when the answer arrives; the payload has no comment text) and `low_satisfaction` (rolling average of the window below the configured limit with enough answers). Both use the existing dedupe, wallboard, acknowledge and email flow.
- **People.** The wallboard has a "satisfaction today" tile (tiles.csat, null when off). The agent's profile progress has a feedback block: own average, satisfied share, the previous period (neutral wording, no red or green), the branch average as an aggregate only, a trend and the latest own comments. There is no leaderboard.
- **Data protection.** Comments are personal data and can identify a visitor. They are stored with the visit and fall under the same retention and erasure story as visitor data (`privacy.commentDays`, default 365 days; the retention job and erasure requests clear `csat_responses.comment`, keeping the score; see D56). The alert payload, wallboard and status API never carry comment text; only reports and the agent's own profile do.
- **Not done.** `printFeedbackQr` (printing a feedback QR on the ticket): the ticket already prints the status-page QR, which shows the card after the visit, so a second code would only duplicate it. Migration `0012_csat_language` adds `csat_responses.language`; the table itself existed since `0000`. The timestamp column keeps its name `at`.

## D54: Natural Arabic announcements

- **Problem.** A call was built from many tiny isolated clips (phrase, letter, each digit, desk phrase, desk digits), each with its own silence and level, played back to back, and announced in Arabic and English by default. It sounded robotic. Requested by the product owner, whose visitors are mostly Arab.
- **Reading.** `src/domain/display/arabic-speech.ts` (pure, no browser) turns a ticket into speech units: "رقم" + prefix letter + a real Arabic number + (optionally) "تفضل إلى المكتب" + the desk number. Numbers use the masculine nominative forms that suit "رقم" and the masculine noun "مكتب" (3 = ثلاثة, 13 = ثلاثة عشر, 14 = أربعة عشر, 105 = مئة وخمسة, 999 = تسعمئة وتسعة وتسعون; thousands up to 999 999, then digit by digit). Latin prefix letters are named as Arabic speakers do (B = بي, C = سي); Arabic prefix letters use their letter names. Words live in one dependency-free file, `src/domain/display/arabic-words.ts`, shared by the composer and the clip generator. Leading zeros are dropped (A-014 is 14); Eastern digits are accepted.
- **Settings** (`voice` setting, all with defaults, none hard-coded): `callLanguages` ar (default) / en / ticket (the visitor's language chosen at reception) / both_ar_en / both_en_ar, replacing the old `mode` + `languages` pair (stored old values are ignored, a missing `callLanguages` means Arabic only; no migration); `ticketReading` letter_then_number (default) / number_only / digits; `announceDesk`; `repeat` 1-5 (default 2) and `repeatGapSeconds` 0.5-10 (default 4); timing `gapPhraseMs` 180, `gapLetterNumberMs` 120, `gapDeskMs` 350, `gapChimeMs` 250, `overlapMs` 0; `chime`, `chimeVolume`, `volume`, `rate` (browser voice), `speed` 0.8-1.25 (recorded voice; it also shifts the pitch slightly, so only a small range is offered). A screen can override `callLanguages`, `repeat`, `volume`, `rate` and `enabled` in its config. For the browser voice the editable template is still used, with the ticket and desk written as Arabic words; "announce the desk: off" removes the template clause that contains {desk} (clauses split at commas) or keeps just the ticket. A recorded pack always says its own fixed wording.
- **Pack format** (`public/audio/ar/<id>/manifest.json`, clip key to URL): `ar.phrase.number`, `ar.phrase.desk`, `ar.num.N` (whole numbers 0..999 as natural connected words, plus 1000..10000 by thousands), `ar.word.thousand`, `ar.letter.A..Z` and Arabic letters, and `ar.digit.0..9` (aliases of `ar.num.0..9`). Files are `num-N.mp3`, `letter-X.mp3`, `phrase-number.mp3`, `phrase-desk.mp3`, `word-thousand.mp3`. "Full" packs (Hamed, Zariyah, Laith) have every number 0..999; "core" packs have 0..100 and the hundreds and compose the rest from two or three clips. The player falls back gracefully: own clip, then hundreds + rest, then ones + tens, then digit by digit; an old pack that only has digits still works. Custom packs may supply any subset of this.
- **Clips are conditioned at generation time**: trimmed to 35 ms lead and 50 ms tail of silence (about 85 and 80 ms once decoded, because of the mp3 encoder delay, which the scheduler subtracts from the configured pauses), 6 ms edge fades, brought to a common gated RMS of -20 dBFS with a -1 dBFS peak ceiling, written as mono 22.05 kHz 32 kbps mp3 (24 kHz at 32 kbps is broken in lamejs, which silently picks another rate). Offline: mp3 decode with `mpg123-decoder`, encode with `@breezystack/lamejs`, no ffmpeg. `node scripts/build-arabic-voice-clips.mjs [ids] [--only=numbers|letters|phrases] [--full] [--refresh]` generates (Edge neural voices; the Piper voice through `PIPER_DIR`); the raw synthesis is cached in `node_modules/.cache/voice-clips`. `node scripts/check-arabic-voice-clips.mjs` reports duration, peak, RMS and silence per clip and fails outside limits. `npx tsx scripts/render-voice-sample.ts <id> out.wav B-014 3` renders a call exactly as scheduled.
- **Playback** (`src/features/display/voice`): with an unlocked audio context the clips are decoded once (a pack is pre-decoded when the screen loads: phrases, letters, numbers up to 199 and the hundreds; the rest is downloaded and decoded on first use) and scheduled sample-accurately with `start(time)`, so the configured pauses are exact (the fixed clip padding is subtracted) and no `ended` events are awaited. `overlapMs` applies only inside one number. Without a running context it falls back to sequential `Audio` elements. The queue still never overlaps; `clear()` now also stops the rest of the running announcement and its repeat pause at once.
- **Admin.** Admin → Screens → Voice is grouped into cards: What is announced, How many times, Timing (sliders, "Reset to natural defaults"), Sound (voice cards, volume, speeds, chime), and Test (ticket and desk, "Play in Arabic", "Play in English", "Play as configured", exact spoken text). The test uses the same job builder and engine as a screen with the values on the page, saved or not.
- **Voices added**: Zariyah (Saudi female), Laith (Syrian), Amany (Syrian female), next to the existing seven. After upgrading run "Add the bundled voices" (or `npm run voice:install-arabic`) so stored manifests are refreshed; old manifests keep working through the digit fallback.
- **Choices to confirm by ear.** A is "إيه" and E "إي" (to tell them apart); the desk phrase is "تفضل إلى المكتب" (addressed to a man; "الرجاء التوجه إلى المكتب" is neutral). Numbers of 1000 and above omit the connecting "و" when composed from clips. The licence caveat of D35 still applies: the Microsoft clips come from the unofficial Edge read-aloud service and the Piper dataset licence is unconfirmed; regenerate with an Azure Speech key or record your own clips under the same names before shipping.

## D52: Visitor notifications

- **Channels and providers.** WhatsApp, SMS and email behind one `MessageProvider` interface. Every adapter returns `{ok, providerMessageId?, error?, retryable}` and never throws. WhatsApp is the Meta Cloud API called with `fetch` (no SDK); SMS is a generic HTTP gateway described by environment variables (URL, method, auth header, JSON or form body with `{to}` `{text}` `{from}`, id path in the response) with a Twilio preset; email is the existing SMTP. `MESSAGING_MOCK=true` swaps all three for the in-memory outbox. Secrets live in the environment only (as SMTP always did), never in the database or the admin UI; the admin sees "configured / not configured / test mode". Requests time out after `MESSAGING_TIMEOUT_SECONDS`; network errors, 408/425/429 and 5xx are retryable, other 4xx are not.
- **Policy is a setting.** Group `notifications` (organization default, branch-overridable): master switch, `requireConsent`, per event (`ticket_issued`, `turns_away`, `called`, `no_show`, `completed_thanks`) an on/off and a per-channel switch, `channelOrder` (default WhatsApp, SMS, email), and volume limits: most messages per ticket (5), attempts per channel (4), retry base (30 s, doubling), rate per minute per provider, and the opt-out footer text. There is deliberately **no quiet-hours or time-of-day rule**: only volume limits.
- **Who gets a message.** Only a visitor who agreed at reception (`tickets.consent_at`), has not opted out, and has a phone (on the visitor) or an email (intake field `email`). A ticket with no contact writes nothing to the log. A ticket with contact but no consent, an opt-out, or the limit reached writes a `skipped` row with the reason. Language is the ticket's language. `completed_thanks` is off by default.
- **Outbox.** `recordEvent` notes the events that matter, and `withBranch` writes one `queued` row in `notifications_log` per notification **inside the branch transaction** (in a savepoint, so a failure there is logged and never breaks issuing or calling; a rollback leaves nothing). After commit the ids go to the job runner; the 15-second maintenance loop re-queues rows whose job was lost (`next_attempt_at` is also the lease of a row being sent). Sending is fire-and-forget: issuing and calling never wait for a provider.
- **Dedupe and limits.** `dedupe_key = "<ticket>:<event>"` is unique, so one event is never sent twice for a ticket, whatever the retries or the number of nodes. The per-ticket cap counts queued, sending and sent rows.
- **Turns away.** Not a timer: before each mutation the waiting positions of visitors with a record are noted; after it, a visitor whose position moved from beyond `visitorStatus.notifyTurnsAway` to within it gets one `turns_away`. A ticket that is already close when issued only gets the issue message. The extra branch reload is skipped unless a waiting visitor has a record.
- **Delivery.** Job `notifications.deliver` claims the row atomically, then walks the channels stored on the row: not configured, no template or no recipient means the next channel; a permanent failure or `maxAttempts` exhausted on a channel falls back to the next one; a temporary failure is retried after base x 2^(n-1) seconds. Over the provider's rate limit the row waits and the attempt is not counted. Final status: `sent`, `failed` (something was tried), or `skipped` (nothing usable). Without the worker (tests, CLI) the handler runs inline and retries happen at once.
- **Templates.** Reuse `message_templates` (channel x event, Arabic and English). Built-in bilingual defaults (Arabic first) apply until an administrator edits a template and are also seeded. Placeholders: `{number}` `{ticket}` `{name}` `{desk}` `{wait}` `{ahead}` `{branch}` `{reason}` `{link}` `{feedbackLink}` `{stopLink}`. A line containing an empty `{feedbackLink}`, `{wait}` or `{name}` is dropped. `providerTemplate` (existing column) is the approved WhatsApp template name for business-initiated messages; its body parameters are the placeholders in order of appearance. `buildTemplateVars` in `src/server/notifications/vars.ts` is the single place variables are defined; other modules call `registerTemplateVars(fn)` to add some (the feedback module supplies `feedbackLink` this way). Providers run at send time.
- **Opt-out.** Every SMS and email ends with the footer setting containing `{stopLink}` = `/t/<token>/stop?s=<HMAC>`. The page asks for a tap to confirm (so mail scanners cannot unsubscribe anyone), then sets `visitors.notifications_opt_out`, honoured on every channel and later visits, and cancels pending messages. WhatsApp session texts carry no footer (template messages cannot); replying STOP is not processed because there is no inbound webhook yet.
- **Status page opt-in.** A visitor with no phone on the ticket, while a phone channel is usable, sees a small "Get updates on your phone" block (number and a consent tick). It stores the number on the ticket's visitor (or links a returning visitor) and sets the ticket consent. It does not send a catch-up "your number is" message.
- **Admin.** Admin, Notifications (permission `admin.access`; organization parts need `settings.manage` / `templates.manage`): channel cards and a test send (organization-wide, `settings.manage`), event x channel matrix, channel order, limits and footer (branch scope shows events and order only, with "use the default"), message editor with variable chips and a live preview in both languages, and the delivery log with masked recipients, filters and resend. A city admin sees only the log of their branches and can override events per branch.
- **Privacy.** The log stores only the masked recipient and non-personal variables (position, wait). The name and the number are read from the visitor at send time, so retention that clears them also stops later messages (`no_recipient`).

## D56: Data retention and privacy requests

- **Retention periods** (group `privacy`, organization-wide, Settings, Security & privacy, Data retention; all in days, **0 keeps that kind of data until erased by hand**): `retentionDays` visitor personal data after the last visit (default 365, the old default was 90); `ticketDataDays` free text and intake answers of finished tickets, plus appointment notes (365); `commentDays` feedback comments (365); `notificationDays` recipient and variables of the notification log (90); `auditDays` audit log (365); `credentialDays` expired sessions, invitations, password-reset tokens and screen pairing codes, counted from their expiry (30). Nothing is hard-coded except two safety floors for the audit log: entries of security-critical actions (`auth.`, `user.`, `role.`, `invite.`, `privacy.`, `apikey.`, `webhook.`, `setting.`, `display.`) are never deleted before 365 days and all other entries never before 30 days, whatever the setting says (`src/domain/privacy/retention.ts`). Stored replies of idempotent requests (`idempotency_keys`) are purged after 24 hours as before; no report-export cache exists, so there is nothing to clear for it.
- **Anonymise, do not delete.** Visitor: name, search/transliteration columns, `phone` (the normalised number) and `phone_hash`, company and `last_agent_id` are set to null and `anonymized_at` is stamped. The row, `visit_count`, `last_visit_at`, the ticket and its events/times/outcome stay, so every report total is unchanged. Consequences, on purpose: the phone hash is gone, so the person can no longer be re-linked, and a later visit with the same number creates a new visitor; repeat-visitor counts stop linking across the anonymisation point. Tickets: `intake` becomes `{}` and `notes` null (finished tickets only: completed, no-show, cancelled). Comments: `csat_responses.comment` null, score/NPS kept (this fulfils the note of D53). Notification log: `recipient_masked` null and `payload` `{}` for rows that are no longer queued or sending; status, channel and times stay. Audit, sessions, invitations, reset tokens: deleted. Pairing codes: cleared. Set `ticketDataDays` no longer than `retentionDays`; the job does not cascade from a visitor to the tickets, so a longer ticket period leaves names in intake answers.
- **Job.** `runRetention(organizationId, {dryRun, batch})` in `src/server/privacy/retention.ts`. Each step selects due rows with `FOR UPDATE SKIP LOCKED` and changes at most 500 per transaction, so locks stay short and two nodes never block each other; a row that is processed stops matching, so a re-run finds nothing (idempotent) and a crashed run just continues next time. The dry run uses the same predicates and only counts, so its numbers equal what the real run then changes. Every real run writes one audit entry `privacy.retention_run` (counts only) which is also the "last run" shown in the UI. Scheduling follows the existing timer pattern (queue maintenance, report scheduler), not pg-boss: `startRetentionScheduler` checks hourly and runs an organization whose last run is older than 23 hours, so it is about once a day from start, survives restarts without doubling, and is not tied to any time of day or opening hours. On demand: Settings button "Run now" and "Preview" (`POST /admin/privacy/retention`), organization-wide `settings.manage` only; they use the saved periods.
- **Data-subject requests** (`src/server/privacy/subjects.ts`, Admin, Privacy requests, permission `visitors.privacy`): find by phone (matched through the keyed hash, any notation), name (Arabic-folded and Latin skeleton) or ticket number; show what is held (counts of tickets, tickets with text, appointments, feedback, comments, notifications); **access export** as JSON or a long-format CSV (`section,record,field,value`, formula-guarded; tickets, appointments, feedback, notification metadata with the masked recipient); **erasure** with a mandatory reason, an explicit confirmation (`confirm: true` in the API, a checkbox in the UI) and an audit entry. Erasure anonymises the visitor now, clears intake, notes, appointment notes, comments and notification details of all their tickets, cancels queued messages and sets `notifications_opt_out`. The opt-out lives on the visitor row; once the hash is gone a new visit with the same number is a new person, which is the price of being unlinkable. Table `privacy_requests` (migration `0014_privacy_requests`: `type` access or erasure, `status`, `subject_kind` visitor or user, `subject_ref`, `requested_at`, `completed_at`, `performed_by`, `note` = the reason, `summary` = counts). `subject_ref` and the audit `entity`/`after` carry only `HMAC(PHONE_HASH_KEY, "subject:<kind>:<id>")`, never a name or number; the reason field warns not to type personal data.
- **Scope.** Retention settings and the run buttons are organization-wide (`settings.manage` held for all branches; a city or branch admin does not even see the section). Privacy requests: an organization-wide holder works on every visitor; a city or branch admin only reaches visitors whose tickets are **all** inside their branches (a visitor who also came to another branch, or has no ticket, is "not found" for them), and sees only the requests they performed in the history.
- **Staff accounts.** `POST /admin/users/:id/actions {action:"anonymize", reason, confirm:true}` (`users.manage`, same branch scope as other user actions) works on a **deactivated** account only: email becomes `anonymized-<id>@deleted.invalid`, display name "Deleted user" / "مستخدم محذوف", phone, password hash, 2FA secret, picture (`user_avatars` row and version), OIDC links, sessions and reset tokens are removed or nulled, the contact details on the invitation they accepted are cleared, `users.anonymized_at` is set. What stays: the user row and id, role grants, agent profile, shifts, every ticket and event they served, and every audit entry (action, entity, time, actor id). What is scrubbed from the audit trail: name/email/phone snapshots in the `before`/`after` of entries about that user, and the IP and browser of entries they performed.
- **UI.** New settings section `retention` (icon, keywords, anchors, search in both languages) with period fields, the last-run summary and Preview/Run now; the old "Retention" card moved out of Data protection (which keeps the consent text). New page `/admin/privacy` and API under `/api/v1/admin/privacy/*`; users dialog gets "Anonymize" for deactivated accounts. Token colours and logical CSS only; no time-of-day, closing or pause wording anywhere (D29, D30).
- **Not done.** No automatic anonymisation of staff; no per-branch retention (policy is organization-wide); appointments are not cleared when a visitor is (only by the ticket period); database backups and logs outside the application are outside this job (see the backup documentation).

## D57: Security review

## D60: Configuration per city

Decided after Milestone 8. Cities are real operating units (different languages, Wi-Fi, numbering, staffing), so configuration is now three levels: **organization default, then city override, then branch override; the most specific wins.** Migration `0016_city_configuration`.

- **Data.** `settings.city_id` (nullable). A row has either a city or a branch, never both (check constraint); one row per (organization, city, branch, key) (`NULLS NOT DISTINCT`). Existing rows are organization-level and keep working. `getSetting(org, key, branchId?, tx)` keeps its signature and resolves branch, then the branch's city, then the organization with **one query** (the city is looked up in SQL; there is no settings cache, so nothing to key by scope). `getSettingSource` (and `resolveSetting`) also returns where the value comes from (`organization`, `city` with its id, or `branch`). Merging is field by field (deep), so a partial city value is completed by the organization's. A branch created later in a city inherits the city's overrides at once (nothing is copied).
- **What a city may override (`CITY_OVERRIDABLE`, one list in `src/server/settings/registry.ts`).** `regional`, `ticketing`, `reception`, `wifi`, `waitEstimate`, `visitorStatus`, `feedback`, `agentWork`, `breaks`, `notifications`, `wallboard`, `displayTheme`, `voice`, `alerts`, `reports`: everything operational that legitimately differs by city (digits, time format, phone code, ticket numbering and reset time, reception flow, Wi-Fi, waiting-time wording, multiple visitors and shift mode, break limits, feedback, visitor notifications, screens and announcements, alert thresholds, report targets). It is a superset of the branch list `BRANCH_OVERRIDABLE`, which is unchanged (a branch still cannot change, for example, ticket numbering). **Not overridable (organization only):** `branding` (company identity: logo, colours, font, texts), `security` (password policy, lockout, 2FA, invites) and `privacy` (retention periods are a legal commitment and the consent text lives in the same group; splitting the group to allow a per-city consent text was left out on purpose). Cities, roles, API keys, webhooks and message-provider credentials are not settings and stay organization-wide. The time zone is a branch column, not a setting.
- **Permissions.** Super admin: organization and any city. City admin: only their own city (`requireCityAccess(branches.manage)`) and the branches inside it; never organization values, never another city (403, and another city's overrides cannot be read either). Branch managers keep their branch overrides. Writes to a non-overridable key at city or branch scope are rejected (`validation`, reason `not_overridable`). Audit: `setting.city_updated` / `setting.city_override_cleared` (the city id is inside `before` / `after` as `{cityId, value}`) and, unchanged, `setting.updated` / `setting.override_cleared` with `branchId`. City entries carry no branch, so only organization-wide auditors see them in the audit list.
- **Admin UI.** Settings has a scope switcher at the top, "Applies to: Organization | City | Branch", deep-linkable with `?scope=city:<id>` / `branch:<id>` and combinable with `?section=`. Each overridable section shows the effective value, a badge of its source, and a copy-on-write toggle ("Override for this city"): turning it on creates the override from the current effective value, turning it off (after a confirmation) deletes it. Sections that are organization-only are shown disabled with an explanation. The Wi-Fi, Waiting time and Feedback sections no longer have their own branch pickers; they use the shared switcher. Cities, Configuration: per city the number of overridden settings, branch overrides and hidden reasons, a link to the city's settings, and "Copy from another city" (super admin; replaces the target's setting overrides and hidden reasons, not branch overrides, shifts or templates).
- **Runtime.** Every consumer already reads settings with the branch id (ticket issuing, display state, wallboard, notifications, feedback, wait estimate, reports, alerts), so the city layer applies everywhere without changes. Changes that screens display (`voice`, `regional`, `branding`, `displayTheme`, `wallboard`) emit `display.refresh` to the screens of the affected branch, of every branch of the city, or of the organization (room `screens:<branchId>` / `displays:<org>`). Reads without a branch (organization-wide jobs such as retention) use the organization value.
- **Shifts.** `shifts.city_id` (null = organization-wide, as before). A city admin creates, edits and archives shifts of their city only; organization shifts stay with the super admin. An agent may pick organization shifts or shifts of the city of their branch. A shift cannot move between organization and cities.
- **Reasons.** Reasons are organization-wide (queues are per branch). `city_reasons` records the reasons a city has switched off (default: all enabled, a later reason appears everywhere). A hidden reason disappears from reception and the status/kiosk lists of the city's branches and cannot be issued or transferred to there (`views.ts`, `tickets.ts`; helpers in `src/server/queue/city-reasons.ts`, which any new issuing path must use). Admin API only so far (below); there is no screen yet, the Cities overview shows how many reasons are hidden.
- **Templates.** `message_templates.city_id`: a city's own wording wins for its branches, otherwise the organization's, otherwise the built-in text (`pickByCity`; used by notification delivery, `sendTemplated`, the print template and the voice templates of the display). API only so far.
- **Not done.** Distribution rules keep their global, branch and queue levels (a city admin edits the rules of their branches; no city level); desks, floors and queues stay per branch. No UI for city templates or hidden reasons, and the notification and voice screens still pick a branch only (the API accepts `?cityId=`). The shifts manager sits inside the Agents section, so with a city selected it is read-only until that city overrides the agent settings. Branch-level copy and per-city consent text are not offered.

## D61: Running a branch without a receptionist

A city or branch may have nobody at the desk. Three ways to issue tickets exist side by side; none depends on the time of day (D29/D30: no pauses, hours or "closed" states anywhere).

- **Reception stays the default and is unchanged** (`tickets.issue`).
- **Agent walk-in issuing.** New permission `tickets.issue_self`, held by the built-in agent role (and every admin role). Chosen over reusing `tickets.issue` so that agents can be given the right without being able to open the reception console, and the reception role needs no change. Setting `reception.agentIssuing`: `off` | `when_no_reception` (default) | `always`, inherited organization, city, branch. `branchHasReception(branchId)` (cached about 60 s) is true when an active user holds, on the branch, its city or organization-wide, a role that can issue tickets but is not an administrator role (administrators are not at the desk). The agent screen shows "New walk-in visitor" only when allowed. It uses the same issue service (reasons of the branch honouring city-hidden reasons, intake fields, consent, numbering, wait estimate), source `agent`. **Serve now** issues, then calls and starts the ticket for that agent at once, without a voice announcement (the visitor is at the desk); it needs the agent to serve the reason and to have free capacity (multi-visitor setting), otherwise it is refused. It changes nothing for other agents' tickets. **Add to queue** is a normal ticket. The ticket prints with the reception print component; with "this computer has no printer" it shows the number and a QR for the visitor's phone.
- **Self check-in kiosk.** A paired device of kind `kiosk` (same `displays` table, pairing code, token hash at rest, revocable). The tablet opens `/kiosk` (no staff sign-in). Device tokens are bound to their kind: a kiosk token is refused by the screen and staff APIs and a screen token cannot issue (`authenticateDevice(token, meta, kind)`). Settings group `selfCheckin` (branch/city overridable): `enabled` (default off), `idleSeconds` (20), `showWait`, `showQr`, `printTicket` (browser print dialog; `--kiosk-printing` for silent printing), `allowedReasons` (empty = every reason a visitor can take alone), `welcomeText`, `maxWaiting` (0 = unlimited) and `ratePerMinute` (12). The last two are volume limits, not time rules. Per intake field `selfService` (default: name, phone, company, email, notes yes; national-ID digits and custom fields no); a reason with `requiresStaff`, or with a required field a visitor may not enter, is shown as "please ask the agent". Abuse limits: per-kiosk rate limit, per-phone limit (3/min), the same phone with a waiting ticket in the branch gets that ticket back, the idempotency key makes retries safe, the cap refuses with "the line is full, ask staff". The kiosk keeps the last reasons list in the browser; with no connection it shows a retry message and never queues anybody by itself. The result screen shows the number, people ahead, the wait (as set in Waiting time), a QR to the status page and returns to the start after `idleSeconds`.
- **Safeguards for admins.** Cities and Branches show "Reception: staffed / not staffed", with one-click "Enable agent walk-in issuing" (writes only `agentIssuing` on the branch) and "Add a kiosk". The overview shows a card when branches have no receptionist, agent issuing off and no paired, enabled kiosk. City admins see only their city.
- **Reporting.** `tickets.source` (reception, agent, kiosk, appointment, api) has a "How tickets were issued" table and export section `bySource`.
- Migration 0017 adds `visit_reasons.requires_staff`. The 0017 snapshot file was not generated (SQL and journal entry are hand-written; run `drizzle-kit generate` once to refresh snapshots).

## D62: Halls and group sessions

A **hall** is a named room of a branch with a **capacity** in which **one agent (the host) receives several visitors together** in one session. It is not "several visitors per agent" (D36), where an agent has independent tickets served one by one at a desk: here the host calls a **group** of waiting tickets at once, the group enters the hall together, one session runs for all of them and each visitor is finished (or all together). The whole feature is opt-in and, like everything else, has no time-of-day behaviour (D29/D30: no pauses, hours, "closed" states or cut-offs; the receptionist and the host control the flow). Migration `0018_halls`.

- **Data.** `halls` (organization, branch, optional floor, `number` announced as "hall 2", bilingual `name`, `capacity` >= 2 by check constraint, `zone`, `sort_order`, `archived_at`; the number is unique per branch among active halls through a partial index, so archived numbers can be reused). `hall_reasons` (which hall-delivered reasons a hall accepts; no rows = all of them). `hall_sessions` (hall, host agent, status `OPEN` -> `IN_SESSION` -> `CLOSED`, or `CANCELLED`; `capacity` snapshot at the call so reports stay true; `reason_id` in same-reason mode; `called_at`, `started_at`, `closed_at`, `outcome`). Partial unique indexes allow **one live session per hall and per host**. `hall_session_tickets` (session, ticket, status `CALLED | ENTERED | NO_SHOW | DONE | RELEASED`, `called_at`, `entered_at`, `finished_at`, `outcome`; unique per session and ticket). `visit_reasons.delivery` (`desk` default | `hall`). `agent_profiles.current_hall_id` / `default_hall_id` (signed in to / usually hosts). `tickets.hall_id` / `hall_session_id` (set while the visitor is in a session; cleared when the visitor goes back to the queue; kept as history after the visit). Existing rows and behaviour are untouched (all new columns are nullable or default to desk).
- **Routing.** A reason with `delivery = hall` is served only by hall sessions; a `desk` reason never goes to a hall. The engine gets two flags (`EngineTicket.hall`, `EngineAgent.inHall`): hall tickets are excluded from `dispatch`, sticky/push/hybrid reservations, `selectTicketForAgent` ("call next") and manual assignment/transfer to an agent (`hall_reason_no_agent`), walk-in "serve now" is refused for them, and a host gets no desk work (`callNext` answers `hall_mode`). They stay WAITING in the reason queue with position and estimate. Switching a reason to hall delivery releases the desk reservations of its waiting tickets.
- **State machine unchanged.** No new ticket status or action. A session maps onto the existing transitions: call group = WAITING -> CALLED (to the hall, `desk_id` null, `serving_agent_id` = host), visitor enters = CALLED -> SERVING (`started_at`), close = SERVING -> COMPLETED and CALLED (never came) -> NO_SHOW, release = CALLED -> WAITING (`requeue`) or SERVING -> WAITING (`transfer`) with the **original queue time kept**, so the visitor returns to their place (event `HALL_RELEASED`). All existing ticket actions (start, complete, no-show, hold, cancel, transfer, recall, undo) still work on a hall visitor and the session **follows the ticket** (`syncHallTicket`, which the ticket service calls after every action; it also starts the session when everyone has entered, if set, and closes it when nobody is left). Undo of a hall visitor is refused once the session is closed. Ticket events carry `{hallId, sessionId}`; hall CRUD is audited (`hall.created|updated|archived`).
- **Domain (pure, tested).** `src/domain/halls/plan.ts` `planHallBatch({waiting, capacity, minGroup, maxGroup, groupMode, reasonId?, acceptedReasonIds?, occupied?, size?})`: `waiting` arrives already ordered by the desk queue's ordering (priority and aging, then first come first served), takes up to `min(capacity, maxGroup, size) - occupied`, one reason per session in `same_reason` (the head of the line's reason, or the first reason that can fill `minGroup`), mixed in `any_reason`; below `minGroup` nobody is called (`below_min`; a top-up ignores the minimum). `state.ts`: member and session status maps, `nextSessionStatus`, `occupancyPct`. `announce.ts`: `planGroupAnnouncement` (list / range / group-only, `maxAnnounced`).
- **Wait estimate.** For a hall reason: `ceil(ahead / capacity)` sessions in front, shared between the halls that accept the reason (rounds = `ceil(sessions / halls)`), times the session length, through the same rounding, buffer and range as D47 (`estimateHallWait`). The session length is the reason's expected minutes or, in analytics mode, learned from the completed visits of that reason (a hall visit's `started_at` is the moment it entered, so it measures the session). `BranchContext.waitFor` is the one place that picks the desk or hall formula (positions, issue confirmation, display, status page).
- **Server** (`src/server/halls`, all under the per-branch advisory lock like the ticket service, events published after commit). `callGroup(host, {hallId?, size?, reasonId?})`: signs the host in to the hall (one host per hall: `hall_taken`), plans the batch, opens the session, calls every ticket and publishes `ticket.called` per ticket (with `hallId`/`hallNumber`) plus **one grouped `hall.called`** (tickets, hall number and name, `recall`). A second press while the host's session is open returns it (`created: false`), another host on the same hall gets `hall_busy`, one host on two halls `host_busy`. `sessionAction(session, {action})`: `enter` (ids or all), `start`, `release`, `no_show`, `recall` (one grouped recall), `top_up` (before the session starts, within capacity, setting `allowTopUp`), `close` (outcome for all or per visitor; visitors who never came become NO_SHOW), `cancel` (before anyone entered; everybody returns to the queue). Every action is idempotent. Only the host (or a holder of `tickets.reassign`) may act. A host with a live session cannot go on a break, away or offline, or change place (`hall_session_open`); the break line and shift rules are otherwise unchanged. The automatic recall and no-show timers (D17) apply to visitors at the hall door: the group is recalled together, and visitors who do not come become no-shows (or return to the end of the queue by the existing no-show action). Hall occupancy is live in the agent workspace snapshot (`hall` console), the display state and the wallboard.
- **Settings** (group `halls`, organization default, city override, branch override like D60): `enabled` (false), `groupMode` (`same_reason` | `any_reason`), `minGroup` (1), `maxGroup` (0 = hall capacity), `allowTopUp` (true), `autoStartWhenAllEntered` (true), `announceMode` (`list` | `range` | `hall_only`, default list), `maxAnnounced` (6; more numbers are read as ranges, or as "the next group"). The no-show handling reuses the existing call timeout settings; nothing here depends on the clock.
- **Permissions.** `halls.manage` (group `services`, given to the same roles as `branches.manage`: super admin and city/branch admins within their scope) for hall CRUD; hosting needs `agent.serve`. A reason's `delivery` is edited with `reasons.manage`. A user's default hall (`agent.defaultHallId`) must belong to the agent's branch.
- **Admin UI.** Halls next to Desks in the branch admin; reasons have "Served at: Desk | Hall"; the user dialog's agent section chooses the default desk or hall; Settings, Agents & service, "Halls"; the coverage card treats hall-only reasons without enabled halls, an accepting hall or a host as a gap (D61).
- **Screens and voice.** Displays show a hall call as a group card ("Hall 2: A-014 · A-015 · A-016", flash, wrap, "+k"), the voice composes "الأرقام بي أربعة عشر، بي خمسة عشر، وبي ستة عشر، تفضلوا إلى القاعة اثنين" from the existing number and letter clips plus the phrase clips `group_numbers`, `and`, `please_go_to_hall` (and friends), falling back to the browser voice when a pack lacks them; announce mode, call languages, repeats and gaps come from the existing voice settings.
- **Reporting and visitors.** Export section `byHall` and an overview card: sessions, average group size, occupancy (visitors that entered / capacity), average session length, no-show rate; filter by hall; hall visitors also flow into every existing KPI. The status page says where to go ("Your group is called: please go to Hall 2"); the notification variable `{hall}` is available for the `called` event and the default wording mentions it only when present.
- **Not done / limits.** No hall-specific working schedule or opening state (by decision). The estimate assumes all hall sessions of a reason last the same time. A visitor can be in one session only. Appointments to a hall reason work as for any reason (no booking of a place in a specific session). Hosting from two browsers at once is the same host and is idempotent.

## D64: Calling by the last digits of the phone, and restarting numbers during the day

- **Calling by phone** (setting `ticketing.callByPhone`, off by default; `callByPhoneDigits` 2-6, default 3). For desks without a ticket printer: reception types the visitor's phone number in a field above the reasons (the number does not have to belong to a reason's intake fields), and the ticket stores only its last digits in `tickets.call_code` (the number itself is not kept). The screens, the wallboard-style desk list and the voice then show and say those digits instead of the ticket number ("Phone ending in 4 7 2"), read digit by digit; the ticket number stays on staff screens next to a small phone badge. Reception must type the number (at least the digits) for tickets it issues; kiosk, agent and appointment tickets may carry one but do not need it. Two visitors in the line cannot share the same digits: the second is refused ("ask for another number"). The voice sentence is the editable template `ticket_called_by_phone` (defaults in `BY_PHONE_PHRASES`); recorded packs have no clips for it, so the sentence voice or the browser voice speaks it.
- **Restarting numbers** (setting `ticketing.numberResetAfter`, 0 = off). After that number the next ticket is 1 again (A-100, then A-001) during the same service day. Each restart bumps a `cycle` on the day's counter and on the ticket (unique per branch, day, prefix, cycle and number), and a number still held by a waiting or served visitor is skipped, so two visitors in the line never share a ticket number; when every number is taken the issue is refused as before (`range_exhausted`). The daily reset time is unchanged.

## D63: Arabic call read as one sentence (voice provider "cloud")

- **Problem.** The recorded packs play a call as separate clips ("رقم", letter, number, desk phrase, desk number), each synthesised alone, so the joins sound unnatural, most of all around the ticket and desk numbers.
- **Decision.** Provider `cloud` ("Natural sentence voice (online)") sends the whole Arabic announcement (the editable template with the ticket and desk as words) to `GET /api/v1/display/tts?text=&voice=`, which renders it as ONE utterance with the neural voice that belongs to the chosen pack (`src/domain/display/edge-voices.ts`) and returns an mp3. Screens authenticate with their device token, the admin voice test with the staff session. Rendering runs in a small child process (`src/server/display/edge-speak.cjs`), because the speech library's WebSocket code breaks when bundled into Next.js. Results are cached on disk by (voice, text) in `TTS_CACHE_DIR` (default: the system temp folder), so each distinct sentence is synthesised once; a screen asks for the audio while the chime plays.
- **Fallback.** Order is cloud, then the recorded pack, then the browser voice; the engine now tries the next provider when one fails to speak, not only when it does not support a step. English is unchanged.
- **Caveat.** It uses the same unofficial Edge read-aloud service as the clip generator (see D35): the server needs internet the first time each sentence is spoken (about 5 s, then instant), and it is for evaluation. For production use an Azure Speech key (same voice names) behind the same endpoint.

## D59: End-to-end and load testing

Decided in Milestone 8 part 4. Details: [testing.md](testing.md), [load-testing.md](load-testing.md).

- **Four layers.** Unit and integration (Vitest) as before; end-to-end browser tests (Playwright, `tests/e2e`, `npm run test:e2e`); load tests (`scripts/load`, `npm run load:smoke` / `load:full`). Playwright specs and the load scripts are outside the Vitest globs, so `npm test` is unchanged.
- **Hermetic by construction.** Each of the two new layers starts its **own** production app (ports 3200 and 3201) on its **own** database (`dor_e2e`, `dor_load`, dropped and re-created every run; names must end in `_e2e` or `_load`, port 3000 is refused). Shared code is `scripts/lib/harness.ts`. `E2E_DATABASE_URL` / `LOAD_DATABASE_URL` default to the bundled PostgreSQL on 5433; CI points them at its Postgres service. Messaging is the mock provider.
- **Production build, not dev mode.** A browser suite needs warm pages; dev mode compiles each page on first visit. The harness builds into `.next-e2e` (rebuilt only when sources are newer) or uses a finished build named in `E2E_DIST_DIR` (CI builds once and passes `.next`). The cost is one to five minutes of build; the build runs before the database is created so migrations added meanwhile are applied.
- **Locators use the shipped wording** (`messages/*.json` loaded in the tests), roles and labels; no `data-testid` was needed. State is set up through the API and awaited by polling, never by fixed sleeps; one worker, scenarios independent through `cleanSlate()`; shift enforcement is switched off in that helper so no test depends on the time of day (D29, D30 stand: nothing in the tests or the product adds hours, pauses or closing states).
- **Load model.** Simulated clients make the same calls and follow the same refetch-on-event rule as the screens (debounce 150 ms, one refetch in flight per query), each with its own address through `X-Forwarded-For` (`TRUST_PROXY=true` on the private instance). Correctness is judged from the database: no lost ticket, no ticket or agent double-booked, numbering unique and gap-free, counts agree, notifications settled. Latency, error rate, realtime delivery, event-loop lag, memory and pool saturation have thresholds; the smoke profile uses limits five times looser (a CI regression gate), the full profile the stated ones.
- **Result.** On the shared development PC the full profile does not meet its latency limits: PostgreSQL work per queue event (branch lock plus the refetch fan-out of every screen) saturates the 20-connection pool while the Node event loop stays healthy; a larger pool made it worse. All queue invariants held in every run. No quick, safe fix was found (no missing index), so none was made and migration number `0015` was not used; the ideas are in load-testing.md for a later decision.
